# 分层架构与解耦

## 1. 三层架构

典型的 Web 项目常按职责拆成三层：

```text
Controller（控制层） → Service（业务层） → Dao / Repository（数据访问层）
```

| 层次 | 主要职责 |
| --- | --- |
| Controller | 接收请求、校验和转换参数、调用业务层、返回响应 |
| Service | 编排业务规则与业务流程，例如下单、库存校验、权限判断 |
| Dao / Repository | 访问数据库、文件或其他持久化数据源 |

调用方向通常从 Controller 向下到 Service，再到 Dao；上层不应直接承担下层职责。

## 2. 什么是分层解耦

**分层**：将不同职责的代码放到不同层中。

**解耦**：一层依赖另一层提供的能力，而尽量不绑定其具体实现。一般让上层面向接口编程，例如 `UserController` 依赖 `UserService` 接口，而不是写死某个实现类。

```java
public interface UserService {
    List<User> list();
}
```

这样更换实现、编写单元测试或扩展业务时，影响范围更小。

## 3. 手动 `new` 的问题

不使用容器时，依赖通常会层层手动创建：

```java
class UserController {
    private final UserService userService = new UserServiceImpl();
}

class UserServiceImpl implements UserService {
    private final UserDao userDao = new UserDaoImpl();
}
```

问题：

- Controller 直接绑定 `UserServiceImpl`，替换实现要修改源码。
- 依赖层级越深，`new` 的数量和组装逻辑越多。
- 测试时不容易替换为模拟对象。

Spring 的 IoC 容器可以统一负责对象的创建、管理与依赖组装；业务代码只声明“我需要什么”，不再自己决定“怎样创建”。

> 分层解决“职责放在哪里”，解耦解决“层与层如何低依赖地协作”。
